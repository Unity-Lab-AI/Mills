# Mills

A private workspace for a small team: talk to Claude in the browser and have it build and edit files on your own PC, and talk to each other in an end-to-end encrypted chat room. There's nothing to install on your side.

**Web app:** https://unity-lab-ai.github.io/Mills/ (deployed from `main` by GitHub Actions). Everyone uses the same address and signs in with **username + password**.

Accounts are created by an admin (see Accounts). The default account is `mills`; accounts flagged `admin` get an extra **Admin** section.

After signing in you land on the **main menu**: your username in the middle, and the **Work** and **Chat** buttons (plus **Admin** for admin accounts only). Every section has a **← Menu** button at the top left.

## How it works

```
Browser (GitHub Pages UI) ──username+password──▶ Cloudflare tunnel ──▶ Mills hub on the host PC (one process, every account)
   │  Work: holds the folder they opened on their PC                         ├─ runs Claude Code (the host's account) in the Mills folder, per account
   │  Chat: encrypts/decrypts messages locally                               ├─ relays Claude's file edits to that person's browser
   ◀── file edits (list/read/write/delete/mkdir) applied in the browser      └─ stores chat ciphertext only
```

## Host: running it

1. Double-click **`bridge/start.bat`** and leave the window open. One window serves every account.
   - The first time, it asks for the `mills` account password if none is set.
   - It starts a Cloudflare tunnel and posts the address to the `Mills bridge address` gist on the GitHub account `gh` is logged in to, where the web app finds it automatically.
2. Requires Node.js, Claude Code (logged in), `gh` (logged in), and `cloudflared` (path set in `bridge/config.json`).
3. Restarting is safe: passwords live in `auth.json` files and are only written by `set-password.js` or the Admin section; device locks live in each account's `state.json`; sign-in sessions live in `bridge/hub-state.json`. Nobody is signed out or asked for a new password when the hub restarts.
4. **What Claude may run.** `allowedTools` in `bridge/config.json` is the complete list of tools a Work run may use without asking (a web session cannot answer a permission prompt, so anything not listed is refused as "requires approval"). Besides reading / editing files it allows exactly the commands the worktree workflow needs: `git status / diff / log / add / commit`, the regression suite (`node bridge/test/regress.js …`) and the worktree tool (`node bridge/worktree.js …`, which also pushes develop, and whose `live` command ships develop to main and restarts the hub when the person asks). Nothing else runs in a shell. Unity in the chat room never gets any of these. The MCP tool groups a Work run gets are `mcp__pc` (the person's PC), `mcp__board` (team board) and `mcp__team` (team chat + presence). Changing the list takes effect after a hub restart.
5. The models offered in the Work model dropdown come from `models` in `bridge/config.json` (`id` = what `claude --model` accepts, `label` = what the person sees).

### Restarts after code or config changes (Claude does this itself)

The window runs `bridge/run.js`, a small supervisor that owns the Cloudflare tunnel and runs `bridge/server.js` (the hub) underneath it. After Claude changes hub code or config it runs:

```
node bridge/restart.js
```

The hub restarts itself the moment nobody has a Claude reply in progress, under the same tunnel, so the address does not change and the web app shows "Mills is restarting" for a second and carries on. `node bridge/restart.js --hard` closes the window and relaunches `start.bat` (new tunnel address, found again automatically) for a wedged hub; `--hard --delay 30` does that 30 s later from a detached helper so the Claude run that asked for it can finish its reply; `--stop` closes it without relaunching. Progress of a hard restart is written to `bridge/restart.log`. Admins can also press **Restart hub** in the Admin section.

### Accounts

Admins manage accounts from **Admin** in the web app: create an account (a 20-character password is generated and shown once), give someone a new password, reset a device lock, sign someone out, stop their Claude run, delete an account (its folder moves to `bridge/profiles-deleted/`, nothing is destroyed). Admin can also clear the chat history.

On disk, the `mills` account is `bridge/auth.json` + `bridge/state.json` + `Mills/Archive/`; every other account is `bridge/profiles/<name>/` (`config.json`: `{ "user": "<display name>", "admin": true|false, "model": "<default model>" }`; the whole `bridge/profiles/` folder is gitignored, so names, admin flags and password hashes never leave the host) + `Mills/Archive/<name>/`. From the command line: `node bridge/set-password.js --profile <name> "password"` (no `--profile` = the `mills` account). `node bridge/master-logins.js` gives every account a new generated password and writes the whole list (username, password, display name, admin) to `Mills-master-logins.txt` on the host's Desktop — outside the Mills folder on purpose, so Claude runs in the hub never see it; device locks and sign-ins are untouched. An account whose `config.json` goes missing keeps signing in with its password (display name = username, not admin) and the hub window prints a warning, so recreate the file to restore it. Everything in `bridge/config.json` applies to every account unless the account's own `config.json` overrides it; an account's `model` is what the Work dropdown's "Default" option means.

## Using it

1. Open https://unity-lab-ai.github.io/Mills/ in **Chrome or Edge** (on Linux: Chrome, Chromium or Brave; Firefox cannot open folders) and sign in with your username and password.
   - **Any screen.** Desktop and laptop get the side-by-side layouts; on a phone or small tablet (up to 700 px wide) everything becomes one column: the chat's conversation list is a drawer (☰, closes when you pick one), Work's panels stack, the board shows one column at a time (swipe sideways) and opens tasks as a full-screen sheet, the calendar becomes a day-by-day list, dialogs fill the screen, controls are finger-sized and typing in a box never zooms the page. Opening a folder on your PC still needs a desktop browser.
2. **Work** is the Claude workspace. Click **Open folder on my PC** and pick the folder Claude should work in, then chat with Claude. It creates and edits files in that folder, and you can edit them yourself in the editor panel.
   - **Layout.** The bar on the far left (☰ widens it to show labels) has a button per panel: **Folder**, **Editor**, **Claude**, **Team chat**, plus **Settings**. Each button shows or minimizes its panel; every panel also has a **—** minimize button. Drag the thin separators between panels to resize them. **Team chat** opens the chat room inside Work, next to Claude; **Pop out** turns it into a window you can drag by its title bar and resize from its corner, **Dock** puts it back. The layout is remembered per account in that browser.
   - The message box never locks: while Claude is replying, **Queue** lines a message up for right after this reply (queued messages show dashed; ✕ removes one), and the second button is **Stop** when the box is empty or **Send now** when it has text, which stops the current reply and sends your text immediately, ahead of the queue.
   - **Sharing your Work session.** The **Share with everyone** button above the Claude messages shares your session with everyone (there is no per-person sharing). The same button then reads **Stop sharing**; signing out stops it too. Everyone in that conversation gets a pop-up and a **Join work** button in the chat, which opens a **watch-only window** of your session: your Claude conversation as it happens (from the last ~150 entries when you started sharing), **what you are typing, live**, what you send and what is **queued**, and a dot that pulses while your Claude is working. Watchers cannot type into your session. Each person still works in their own session and their own worktree; open several watch windows to follow several people (drag them anywhere, ✕ to close). **Summaries:** while you have watch windows open, every message you send to your own Claude gets a short automatic summary of those sessions appended (the latest few exchanges of each, clearly marked as context, not shown in your chat and not shown to anyone watching you), so your Claude knows what the others are doing.
   - **Usage bar** (just above the Claude messages). **5h** shows how long until the current 5-hour usage window resets (hh:mm:ss), **7d** the weekly window (dd hh mm), each with a small fill bar and a percentage. These limits belong to the host's single Claude account, so everyone shares them.
   - **Percentage:** the % used that Claude Code reports. Until it has reported one, the % (shown as `~NN%`, greyed and marked "est") is how much of the window's time has passed, not usage.
   - **Always in step:** the fill, its colour and the % come from the same number. A window shows empty ("reset") once its reset time passes.
   - **Fresh numbers:** the page re-reads them as each step of a reply arrives, and every 15 seconds otherwise, since other people's runs move the shared limits too. **Context** is how full this session's context window is (tokens used of the model's window): the bar slides from green through orange and yellow to red as it fills, and turns purple when you are out of usage (context full, or the account hit its limit) — start a **New chat** then. Hover any part for details.
   - **Past sessions.** Your Claude conversations are **auto-saved** (Settings → Auto-save, every 5 minutes by default; 1 / 2 / 5 / 10 / 15 / 30 minutes or Off). The first auto-save names the session itself from your first message plus the date and time, and every later auto-save overwrites that same saved session, so you never have to press anything. **Save session** saves right away (and asks for a name if it has none yet); once saved, a session also updates itself after every reply. **Past sessions** lists them: **Open** (Claude resumes with full memory of it), **Rename** (or click the session title above the chat), **Delete** (click twice). The search box at the top searches titles and everything said in your sessions (every word must match, any case); results are ranked by number of matches and show a snippet of who said what, with the matches highlighted. Esc clears the search, then closes the window. They live on the host PC under `Mills/Archive/` (the folder name is unchanged) and are never committed.
   - The **model dropdown** picks which Claude model answers you (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, or your account's default). It applies from your next message (after the current reply), to every new chat, and survives restarts. Each "Done" line shows which model answered.
   - **My worktree / Shared folder** (top bar) picks where Claude works when you ask it to change Mills itself. **My worktree** (the default) is your own git copy of Mills on the host, `Mills-worktrees/<username>` next to the Mills folder, on branch `work/<username>`, created from `develop` the first time you send a message, so several people can have Claude change Mills at the same time without touching each other's changes. Ask Claude to "merge into develop" when your change is done; going live (develop → main + hub restart) is a separate step that only happens when asked. **Shared folder** is the host's Mills folder itself, the running hub's own checkout that everyone shares. Switching starts a new chat. The host can run `node bridge/worktree.js status | ensure <username> | commit <username> [message] | sync <username> | merge <username> | live [--restart]` (from the Mills folder or from inside a worktree; `commit` stages everything uncommitted in that person's worktree so `merge` can take it; `merge` carries work/<username> into develop and `sync` carries develop back into work/<username>; merges use a temporary checkout that is removed afterwards, so develop stays free to check out in the Mills folder); `"worktreeRoot"` in `bridge/config.json` moves the worktrees folder. **Going live** is `node bridge/worktree.js live --restart` (only when asked): it merges develop into main in the host folder, pushes main and develop to every remote, prints the GitHub Pages deploy run, and asks the hub to restart itself gracefully on the new code; it refuses if the host folder has uncommitted changes and leaves nothing half-merged on a conflict.
   - **Theme** opens 23 UI colour themes plus the Mills default, remembered in that browser.
3. **Chat** is a room shared by every account. Messages are end-to-end encrypted (see Security). The list on the left has **# Everyone** and a **private conversation** with each person (only the two of you can read it). Red numbers count unseen messages per conversation, on the Chat button in the menu and on the Team chat button in Work; the tab title shows the total. Key fingerprints are under **Key fingerprints** at the bottom of that list.
   - **Presence** is hub-wide, not just the chat. Everyone signed in is **online** (green), **away** (yellow: tab hidden, or 5 minutes without input) or **offline** (dim, with "last seen"), and the others can see which part of Mills they're in. The hub counts each page's open connection, so closing a tab, losing the connection or signing out shows as offline within seconds and coming back shows at once. It appears as a dot and status line under each person in the chat list, as "N online" in the chat header, and as a **Who's here** strip on the main menu. "Sam is typing…" appears under the messages for the conversation you're looking at (a private conversation shows it only to the other person); Unity shows as typing while she composes. Typing lapses by itself after a few seconds.
   - **Motion.** New messages slide in, buttons react to the hand, the sign-in status has a live pulse, and Work shows a "Claude is thinking…" bubble until the first words arrive. Everything respects the system's reduced-motion setting.
   - **Markdown in both chats** (Claude's replies in Work and the team chat), rendered by `web/md.js`:
     - Text: headings, **bold**, *italic*, ~~strike~~, ==highlight==, `code`, single line breaks kept.
     - Links: http / https / mailto only, including bare URLs.
     - Structure: nested bullet, numbered and task lists; tables with column alignment; quotes and GitHub alerts (`> [!NOTE]`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`); `---` rules; footnotes.
     - Code blocks: language label, syntax colouring and a **Copy** button.
     - Images: `![alt](https://…)` and inline `data:` images load (lazily, without a referrer; click opens the full size). An `http://` picture is tried over https (the page may only load https) and falls back to a link. A **relative path** such as `![shot](out/shot.png)` is loaded from the folder you opened on your PC in Work (nothing is uploaded; without an open folder the markdown stays as written) — so Claude can show you a picture it just made in your project.
     - Not rendered: `$$` math is shown as source.
     - Safety: the renderer never inserts HTML, so raw HTML in a message stays plain text.
   - **Icons.** The site uses no emoji. Every icon is a custom SVG from one sprite at the top of `web/index.html`: 33 line icons drawn in the text colour, so they follow every theme. Script adds them with `ic(name)` / `label(el, name, text)`. The gear on Claude's tool lines comes from CSS.
   - **Diagrams.** A ```` ```mermaid ```` block draws a diagram (with **Source** and **Copy**). It uses Mills' own copy of Mermaid in `web/vendor/mermaid.min.js`, loaded only when a diagram appears, in strict mode, with the SVG cleaned before it is shown. To install or update it, run `node bridge/vendor.js` from the Mills folder (or `node bridge/test/regress.js --install-vendor`, which does the same and then runs the regression suite; that form is one of the commands Claude may run from a Work session): it fetches Mermaid 11 from the npm registry, verifies the package against the registry's published integrity hash before unpacking, writes `web/vendor/mermaid.min.js`, and records the version and sha256 in `web/vendor/VENDOR.json`; then commit both files. `node bridge/vendor.js --check` verifies the files on disk, and regression check R102 does the same. Without the file, diagrams show their source with a note.
   - **Click a message** to **Reply** (your message shows a quote that jumps back to the original), and on your own messages **Edit** or **Delete** (click twice). Edited messages say "edited"; deleted ones leave a "message deleted" marker. Times are shown in your own browser's time zone (hover for the full date).
   - **Receipts.** Under your messages: "seen alex · unseen sam" — who has looked at that conversation since. Any message's menu shows the same for it.
   - **@mentions.** Type `@` and pick a person (Tab / Enter takes the first match), or write `@username` / `@nickname`. Mentions of you are highlighted.
   - **Sounds.** Three different tones: a normal message, an @mention of you (or a private message to you), and a reply to one of your messages. Each has its own volume slider in Settings. No sound plays for the conversation you are looking at.
   - **Read aloud (optional).** Turn on "Read new chat messages aloud" in Settings and new messages are spoken one after another ("Alex: …", "Alex privately: …", "Alex replied: …") with your browser's built-in voices, so you can keep working and just listen. Settings has speech volume, speed, voice (with ▶ to try them before saving), whether to read every message or only @mentions / private messages / replies to you, and a button to stop and clear the queue. Code blocks and links are not read out; messages in the conversation you are looking at are not read.
   - **Dictation (🗣).** Next to Send in the team chat and in the Claude box in Work. Click it and talk: your words are typed into the box after whatever is already there, so you can stop, fix something, and click again to carry on. It stops by itself after about 3 seconds of silence (or click it again, or start typing). It never sends on its own — press **Send** / **Enter** — with one exception: finish with the words **"send message"** and then pause; the button turns green and the message is sent (without those two words). Speaking again during that pause cancels it. Uses the browser's own speech recognition (Chrome, Edge; not available in Firefox, where the button is hidden). Note: in Chrome and Edge the audio is turned into text by the browser maker's speech service, so dictated speech leaves your computer that way; the resulting text is sent end-to-end encrypted like anything typed.
   - **Voice clips.** Press 🎤 next to Send to record (the browser asks for microphone access the first time; the microphone is switched off again as soon as you stop). Up to 2 minutes; **Send clip** or **Cancel**. Anything typed in the box goes along as a caption, and a clip can be a reply. Clips are encrypted end to end exactly like text and play inline with a player; Settings has a voice clip volume and **Auto-play incoming voice clips**, which plays them one after another in the same queue as read-aloud (the stop button clears both).
   - **Voice / video calls.** **📞 Call** (top of the chat) starts or joins the call of the conversation you are in: # Everyone has one shared call, each private conversation its own two-person call. There is no ringing: when someone is in a call you get a notification (one soft tone, a pop-up you can click to join, and a "… is in a call here — Join" bar in that conversation). Joining uses your microphone (listen-only if you do not allow it); **the camera always starts off** and is switched on and off with **📷** even when the browser already allows it (the camera light goes off when you turn it off). **Mute / Unmute** (or the **M** key when you are not typing) switches your microphone, **Leave** hangs up. Whoever is talking gets a green glowing ring around their tile (you too). Each person's tile has its own **🔊 / 🔇** and volume slider (hover the tile): they only change what you hear, are kept in your browser per person, and multiply with the call volume in Settings; closing the tab or signing out leaves too. While the chat is open (Chat screen, or Team chat in Work with its side list shown) the call sits at the top of the chat's side list; otherwise it is a small window you can drag anywhere, and it snaps to the nearest corner or edge when you let go.
     - **End-to-end encrypted.** Audio and video go straight between the browsers over WebRTC (DTLS-SRTP). The hub only passes on the connection set-up, and those messages are encrypted with the same per-person chat keys, so the hub can neither listen in nor put itself in the middle. Compare key fingerprints once to be sure nobody swapped a key.
     - **Codecs.** Opus for voice (≈32 kb/s, error correction for lossy networks, near-silent when nobody talks); video prefers VP9, then AV1, VP8, H.264. All are decoded by the browser itself. Settings → Video quality: low 320×180 / medium 640×360 (default) / high 1280×720.
     - **Microphone processing** (Settings, used for voice clips and calls): noise suppression (on by default), echo cancellation and automatic level, each switchable; changes apply to a call in progress. Settings also has the call volume.
     - **Networks.** Browsers find each other with a public STUN server (Google's by default: it learns each browser's public IP address, never any audio or video). On very strict networks a direct connection is impossible; the host can then add a TURN relay to `"iceServers"` in `bridge/config.json` (standard WebRTC format; TURN only relays encrypted media). Calls are a mesh (everyone connects to everyone), meant for a small team.
   - **Pop-ups.** While you are in Work, new messages float up in the bottom-right corner and fade away (click one to open it). Turn them off in Settings.
   - **Settings** (main menu, the chat header, and the Work bar): nickname (shown with your messages and usable for @mentions), your colour (16 preset colours that stay distinct from each other and adapt to every theme; "auto" picks one from your username), sound on/off, the three volumes with ▶ to test, pop-ups on/off, and the theme. Nickname and colour are stored on the hub so everyone sees them; the rest follows your account.
   - **Unity is in the room too** (on the host's local brain by default, `"roomAgentBrain"` in `bridge/config.json` = a Claude model id to switch back). When she's called she uses the caller's own tools, time and place, can post pictures, and her sign-in hello includes your local time, weather and local headlines.
   - How she is called: She says hi when someone signs in. Otherwise only her own handle calls her: write **`@unity`** (any capitalisation; `@claude` or just "unity" no longer do). Your browser only encrypts a message for her when it contains `@unity` (or is a private message to her), and then sends the **5 messages before it** in that conversation along inside the encryption — so she reads at most the **last 6 messages** and the hub cannot read the rest of the chat. She answers in the room in the lab's Unity persona. A private message to her always gets a private answer that only you receive. It works in the host's Mills folder, so it can also work on Mills itself when asked. The hub won't restart while Claude or anyone else is in the middle of a reply. Set `"roomAgent": false` in `bridge/config.json` to remove it, `"roomAgentModel"` to choose its model, and `"roomAgentName"` to rename it (default Unity).
4. **Board** is the team's task board, shared by everyone and by Claude. The ideas come from HyperProductivityManager.
   - **Columns:** Backlog → To do → Doing → Review → Done. Drag a card between or within columns, or press **+** on a column to add one.
   - **More than one board:** pick one in the header, or add one with **+ Board**. The header also has a filter (title, label, person, id) and **Mine** (assigned to you or claimed by you / your Claude).
   - **A task** has a markdown description (the same renderer as chat, including tables and mermaid), labels, priority P1–P5, a due date, an assignee, a repeat (daily, weekly, every 2 weeks, monthly, quarterly, every 6 months, yearly), and its own activity log.
   - **Repeats:** completing a repeating task moves it to its next due date instead of finishing it. Monthly repeats are month-end aware: Jan 31 → Feb 28 (29 in a leap year) → Mar 31.
   - **Claims.** Before working a task, a person (**Claim 30 min**) or Claude takes a time-limited claim. While it's held, nobody else can edit, move, complete or delete the task. Renew it to keep working; release it or complete the task when done.
   - **Lapsed claims.** A claim that isn't renewed lapses on its own, so a crashed or forgotten run never blocks work. Lapsed claims are flagged in the header and on the card.
   - **No silent overwrites:** saving a task that someone changed since you opened it is refused, and you reload first.
   - **Deletes** leave a tombstone in the board file, and every change goes to an activity log (the newest few show in the footer, next to who has the board open).
   - **Claude works the board too.** Every Work run has board tools (list, read, create, claim, renew, update with a progress note, complete, release). Claude acts as **"<your name> · Claude"** and is told to claim before working. Its claims show on the board in green, and even you can't edit a task your own Claude is holding until it releases it.
   - **Give to Claude** (on a task, or in Work's Tasks pane) puts a ready instruction for that task in Claude's box in Work.
   - **Claude can talk to the team.** Every Work run also has the team tools (`bridge/team-mcp.js` → `bridge/team.js`): `team_say` posts into the team chat as **"<your name> · Claude"** (to # Everyone, or privately to one person with `to`), and `team_presence` tells it who is online, away or offline. Posts are sealed with the hub's own chat key (the one Unity uses), so every member can read them; the "<name> · Claude" label and the person's colour travel outside the encryption. Unity never answers these posts. Claude is told to announce in the chat before any hub restart and when something ships.
   - **Live for everyone** through the same long poll as the chat. The menu's Board button shows how many tasks are due today or overdue for you.
   - **Where it lives:** board data is stored on the host in `Mills/Board/board.json` (never in git). It is **not** end-to-end encrypted, because Claude has to read it, the same as Work runs.
5. **Calendar** is a month view of every task with a due date. As in HyperProductivityManager, a task with a due date *is* the calendar entry, so the board and the calendar can't drift apart. Click a day to add a task due that day, or click a task to open it on the board. Today is highlighted, overdue tasks are red, finished ones are struck through, and repeating ones show the repeat icon.
6. **Work → Tasks pane** (rail button **Tasks**): what you or your Claude hold, what's due within a week (yours or unassigned), and what's assigned to you. Each task has **Claude** (hand it to Claude) and **Open** (jump to it on the board).
7. **Unity** (menu) is Unity as your own assistant. Everything runs on the host PC that runs `start.bat`; you only need the browser.
   - Ask her to add / list / finish tasks (priorities, due dates, notes), add calendar events, set reminders ("remind me in 20 minutes…"), remember things about you, keep a knowledge base, do math, tell the time. Your tasks, calendar, reminders and memory are yours alone (kept in your account's folder on the host).
   - Anything that deletes something shows a **Yes / No** card first and nothing happens until you answer.
   - Due reminders pop up in the bottom-right corner wherever you are in Mills (and as a browser notification if you allowed them).
   - **Time and place are yours:** your browser sends its time zone with every message, so "what time is it" and due times are your local time. **📍 Share location** adds your rough position (rounded to about 100 m) for local answers; click again to stop.
   - The dropdown picks her brain: **Unity (local)** is her own model on the host's GPU (Ollama, `unity-brain`), or any Claude model (uses the host's Claude account). **New chat** starts over; your data stays.
   - **Pictures.** Ask for a picture or a selfie and she makes it on the host's own image engine (`bridge/image-engine.py`: local Stable Diffusion, started by the hub with Python 3.10 + torch + diffusers, checkpoint `assistant.imageCheckpoint`). Selfies are written fresh from the moment (what is going on, where she is, who is with her, the weather where you are) with her look (`assistant.selfieLook`) added after the scene. Long prompts are encoded in pieces, so nothing is cut; there is no negative prompt. Pictures show inline (click to download); private ones only for you, room ones for everyone.
   - **Photos.** 📷 takes a webcam photo, 📎 sends a picture from your PC (shrunk to 1024 px in your browser). It goes with your next message: she sees it (her model has vision) and can change it: **edit** (restyle it, put you somewhere else, keeping your face) or **inpaint** (repaint one area, the rest stays). Your photos and her edits are private to you.
   - **Voice.** 🎤 records your mic (click, talk, click again); the host turns it into text (`bridge/speech-engine.py`, faster-whisper on the CPU, model `assistant.whisperModel`) and sends it. 🔊 plays her replies in her own voice with the emotion she picked (unity-voice-v2 on the host, `assistant.voiceDir`, started by the hub). Both are per browser and nothing is installed on your side.
   - **Web and media.** She can search the web (Bing results, no key), read a public page to answer from it or summarise it (the host never fetches its own network or private addresses for this), and play YouTube: the video plays right in the chat (privacy-enhanced embed). Works in the Unity section and with @unity in Chat.
   - **Your own computer.** She can list, read, write, make folders in and delete (Yes / No first) files in the folder you opened in Work ("Open folder on my PC"); your browser does it, the host never touches your PC. She can also run short JavaScript or Python programs in a sandbox in your browser (a Worker: no page, no cookies, no files; Python via Pyodide, loaded on first use) and read their output. Nothing runs on the host. Admins switch both per account in **Admin** (Unity: PC files / Unity: Run code); they are on unless an admin turns them off.
   - **Weather and news** where you are: your rough place comes from your connection (or 📍 Share location for the exact one); weather from Open-Meteo, headlines from Google News, no keys.
   - Host setup: Ollama installed. The hub starts `ollama serve` itself and loads `unity-brain` from its Modelfile once (`assistant.modelfile` in `bridge/config.json`, default `../Backrooms/models/unity-brain/Modelfile` next to the Mills folder). Her persona text is `bridge/assistant-persona.txt` on the host (never committed); her look in pictures is `assistant.selfieLook`.

### Is my message being worked on?

Every message you send shows a status line under it. **Work:** *Queued* (waits for the current reply), *Claude is working on this… 1 min 20 s*, then *Done in 42 s*, *Stopped* or *Failed* (with the reason). **Unity section:** *Unity is working on this…* then *Done*, *Stopped* or *Failed*. **Chat, a message with @unity:** *Sent to Unity, waiting…*, *Unity is answering…* while she types, *Unity answered* once her reply is in, or *No answer from Unity yet* after 3 minutes.

## Publishing updates

The app is published from `main` (GitHub Pages deploys `web/`). Work follows Git Flow: `feature/<name>` from `develop`, merged `--no-ff` into `develop`, then `develop` into `main`. The Pages workflow fills in the gist owner from the `MILLS_GIST_OWNER` repository variable (Settings → Secrets and variables → Actions → Variables), so no account handle lives in the source. Never commit `auth.json` / `state.json`, `bridge/profiles/`, `bridge/hub-state.json`, `Archive/`, `Chat/`, logs or `.claude/` (all kept out by `.gitignore`).

## Security

- **First sign-in claims an account.** The first browser that signs in to an account becomes the only one allowed into it. To move someone to a new browser, an admin uses **Reset lock** in Admin.
- Passwords are stored on the host PC only, as scrypt hashes. After 5 failed sign-ins for a username, that username is blocked for 15 minutes. Only the GitHub Pages origin may call the hub. The Admin endpoints check the account's `admin` flag on every request.
- **Chat encryption.** Each account has an ECDH P-256 key pair created in its browser. The private key stays in that browser and is also backed up on the hub encrypted with a key derived from the account password (PBKDF2, 310,000 rounds), so it follows the account to a new browser. Every message is encrypted with a fresh AES-256-GCM key, which is wrapped separately for each member. The hub (and its disk, `Mills/Chat/`) only ever holds public keys, the locked backups and ciphertext, and each reader is sent only their own wrapped key. Limits worth knowing: the hub sees your password for a moment when you sign in, so someone who controls the host PC *while you sign in* could unlock your backup; compare fingerprints in the member list once with each other to rule out a swapped key. A password reset done by Admin on someone who then signs in from a new browser starts a fresh key: older messages stay unreadable in that new browser. What the hub can see without reading any message: who sent what when, who a private message is for, whether a message was edited or deleted, and the receipts (how far each person has read each conversation). Deleting a message removes its ciphertext from the hub's disk. **Exception: Claude.** Its private key is kept on the hub (`Mills/Chat/agent-key.json`) so it can read and reply, which means the host PC can read every message sent while Claude is a member.
- **Message format v3** (all new messages and edits). Three extra protections against a hub that tampers with stored messages:
  - **Bound to sender, recipient and id.** Each message carries a random 16-byte id. The sender, the recipient (or none for # Everyone) and that id are authenticated data on the body, and each member's wrapped key is also bound to that member's name. If the hub moves a message to another sender, conversation or reader, it fails to decrypt.
  - **Replays refused.** The hub refuses a second message with an id it has seen. Browsers also refuse a copy of an id under a different seq, and once a sender has used v3, they refuse later old-format messages from that sender (downgrade guard).
  - **HKDF wrap keys.** Wrap keys come from HKDF-SHA256 over the ECDH secret with a fixed label, not the raw secret.
  - **Padded length.** The plaintext is padded to a size bucket (256 bytes, doubling up to 64 KiB, then 64 KiB steps), so the ciphertext length no longer shows how long a message is.
  - Older messages still decrypt the old way.
- **Message format v4** (browsers with `CompressionStream`; older ones keep sending v3):
  - The message JSON is deflate-compressed **before** encryption (length prefix + deflate + padding). The hub only sees compressed, padded ciphertext, and decryption and decompression happen only in browsers.
  - A voice clip's audio is a separate ciphertext with its own key. That key travels inside the encrypted message, so editing the caption keeps the clip. The message list no longer carries clips: a clip is downloaded (`/api/room/blob`, only for that message's readers) and decrypted when someone presses play.
  - Voice and images are already compressed formats, so they are not deflated again.
- **Key pinning.** Each browser remembers every member's public key the first time it sees it. If the hub later hands out a different key for someone, they are marked **⚠ CHANGED** under Key fingerprints: nothing is encrypted to that key, and messages sent with it stay hidden until you compare fingerprints with them outside Mills and press **Trust new key**.
- **Page and hub hardening:**
  - The page has a Content-Security-Policy: it may only talk to itself, the hub's Cloudflare tunnel and the GitHub API, with no outside scripts, frames, plugins or images.
  - The hub address read from the gist is accepted only if it is a `*.trycloudflare.com` address. The last good address is cached, so a page load skips the GitHub lookup.
  - Hub answers carry `nosniff`, `no-referrer` and `X-Frame-Options: DENY`, and API answers are `no-store`.
  - Password hashing runs off the main thread, so sign-ins never stall anyone else. The 5-attempt limit also counts parallel attempts.
- **Faster and in sync:**
  - The chat is pushed by a long poll: the hub answers the moment something changes, instead of every browser asking every 3 seconds.
  - In calls, each person's audio and video are sent as one stream, so the browser lip-syncs them.
  - ICE candidates are sent in batches, so connecting needs fewer round trips through the tunnel.
- Claude can't run shell commands by default. `allowedTools` / `permissionMode` in `bridge/config.json` control that.
